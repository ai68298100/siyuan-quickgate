# 34 · 桥消费权失联检测与接管规格（L571 剩余 + L627）

> 2026-10-07。规格先行（E2）。**实现绑定门槛：双窗口真机场景验证**（Web Locks steal 行为、双窗口竞态均需真机）——规格定稿 ≠ 立即实现；实现时按本文验收，行为变更须回写本文。
> 现状基线：`src/services/bridge-claim.ts`（Web Locks `ifAvailable` 互斥，L452）+ `src/services/poller.ts`（单飞轮询）。

## 1. 背景与缺口

Web Locks 由浏览器保证：**持有窗口死亡（崩溃/关闭）时锁自动释放**——该失联场景已自愈，另一窗口重开桥即可认领。**未覆盖的缺口**：持有窗口**存活但轮询卡死**（主线程长阻塞、循环挂起、存储 IO 永久挂起）——锁仍被持有、消费停摆、命令持续积压，其他窗口诚实拒绝启动，用户无路可走。

相关现状：`SingleFlightPoller` 未暴露 `lastTickFinishedAt`；`bridge-claim.ts` 未处理 `steal`（接管）导致的 release 失败；恢复向导（R337）已能显示"消费权被另一窗口持有"但无动作。

## 2. 目标与非目标

**目标**：其他窗口能**检测**持有方卡死（心跳过期）→ 在用户确认后**安全接管**（Web Locks `steal`）→ 接管全程与接管后**不产生双消费**；接管前显示待处理数与卡死时长（L627 显示语义）。

**非目标**：
- 不诊断/修复持有窗口的卡死原因（那是宿主级问题）。
- 不做跨设备消费权（Web Locks 为单机同源机制；跨设备由 device 路由分工，不变）。
- 不改变"同一时刻仅一窗口轮询"的不变量——接管是**转移**唯一消费权，不是增加消费者。

## 3. 机制设计

### 3.1 心跳（持有方义务）

- 持有窗口在 `SingleFlightPoller` 每次 tick 完成后更新内存 `lastTickFinishedAt`（新增只读属性）。
- 心跳落盘限流：距上次落盘 ≥2s 才覆写 `/storage/petal/siyuan-quickgate/bridge/heartbeat.json`，形状 `{ holder: "<deviceName>#<windowSeq>", ts: ISO, pollMs: number }`（<100B 覆盖写；pollMs 下限 200ms 时最坏每 10 tick 落盘一次——L604 边界自查通过）。
- 落盘失败（存储不可写）→ 静默保留内存心跳；此时检测方读不到新鲜心跳，按 §3.2 退化为"未知"。

### 3.2 检测（任意窗口，桥开启但本窗口无轮询时）

读 `heartbeat.json`：
- `now - ts ≤ 15s`（默认阈值 = 30 个 500ms 周期）→ 持有方健康，显示"消费权被另一窗口持有（心跳正常）"，无接管动作。
- `now - ts > 15s` → **卡死嫌疑**；超过 60s 升级为"高度疑似失联"。两种状态下接管按钮均可见，但**确认文案不同**（见 §3.3）。
- 读不到 heartbeat 文件或内容损坏 → "无法判断另一窗口状态"（诚实），不提供接管。

阈值常量：`HEARTBEAT_STALE_MS = 15_000`、`HEARTBEAT_SUSPECT_MS = 60_000`（写死并导出；不进设置页——内部鲁棒性参数，L458 裁定先例）。

### 3.3 接管（steal）

- 入口：恢复向导检测行的「接管消费权」按钮；确认文案两档：
  - 心跳过期（15s~60s）："另一窗口可能卡死（心跳 X 秒前）。若该窗口仍在使用，请先在其「连接与通道」停用桥再回来接管。将丢弃行数 N 条未消费命令将被本窗口接管消费。确认接管？"
  - 高度疑似失联（>60s）："另一窗口已 X 秒无心跳（高度疑似失联）。N 条未消费命令将被本窗口接管消费。确认接管？"
- 实现：`navigator.locks.request(name, { steal: true }, cb)`（非 ifAvailable）——steal 会立即破坏已持有的锁。
- **双消费防线**（不变量，全部已存在、无需新增）：接管后新窗口轮询以 `processed` 台账幂等跳过旧窗口已消费命令；旧窗口若从卡死中苏醒并尝试继续 tick，其命令读取侧按台账跳过（执行即消费+台账先查），且其后续 release 抛 AbortError（见 §3.4）。**残留风险**（如实登记）：卡死窗口苏醒的瞬间与接管窗口的 tick 存在理论竞窗——台账先查把窗口缩到毫秒级，未归零；文档明示"接管后建议在原窗口停用桥"。
- 接管成功 → 本窗口 `startBridge()` 正常认领路径接管轮询，UI 标注"接管自 <holder> @ <时间>"（L627）。

### 3.4 持有方 release 容错（实现增量）

`createNavigatorClaimer` 的 release 以 `releaseResolve` 收尾——被 steal 后该 promise 的锁回调已被浏览器以 AbortError 打断，`release()` 需 catch（现状 `release: async () => releaseResolve?.()` 不抛，安全；但 claim 回调内部的异常路径要验证）→ 实现时为 claim 回调补 `try/catch`，确保被 steal 后旧窗口不因未处理 rejection 崩溃。

## 4. 边界

| 场景 | 行为 |
|------|------|
| 无 Locks API 环境 | 单窗口假设（现状）；向导不显示接管项 |
| heartbeat 写失败 | 检测显示"无法判断"，无接管（诚实不猜） |
| steal 瞬间原持有者恰好正常 release | steal 请求等同重新竞争——成功则接管，失败则提示重试 |
| 第三窗口同时接管 | Web Locks 保证 steal 串行化，最终只有一个持有者 |
| 跨设备 | 不适用（Web Locks 单机同源；跨设备用 device 路由，不变） |

## 5. 实现切分（I1~I3）

| 增量 | 内容 | 规模 |
|------|------|------|
| I1 | poller `lastTickFinishedAt` + heartbeat 限流落盘 | 小 |
| I2 | 恢复向导检测项 + 两档确认文案（无接管） | 小 |
| I3 | steal 接管 + claim 回调容错 + "接管自"标注 | 中（需双窗口真机） |

## 6. 验收标准（实现时逐条对勾）

1. 双窗口：A 持锁消费，B 打开向导显示"心跳正常"，无接管动作（或确认文案为温和档）。
2. 用调试手段停掉 A 的 tick（保持窗口存活）→ 15s 后 B 显示卡死嫌疑，60s 后升级失联档。
3. B 接管成功 → A 被破坏的锁不产生未处理异常；积压命令由 B 消费，无双执行（台账核对）。
4. A 关闭 → 锁自动释放 → B 正常认领（回归现状）。
5. heartbeat 文件删除/损坏 → 向导显示"无法判断"，无接管按钮。
6. 全程审计与回执连续无缺口（消费权转移不产生回执丢失）。

## 7. 开放问题（实现前需定）

1. `holder` 标识的 windowSeq 如何生成（内存自增即可，但需进 heartbeat 以便"接管自"显示）。
2. 心跳文件是否纳入全量备份/载体明细卡——建议纳入（一行）。
3. steal 在 Electron renderer 的实际行为（Chromium 实现，理论支持）需双窗口真机实证——I3 的前置。
