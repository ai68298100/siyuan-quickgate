# 生态调研 R8 · 通知/收件箱范式（喂 G5-02 深化）

> 循环 C 第 8 轮（2026-10-06）。对象：GitHub Notifications、Linear Inbox、Grafana Alerting、Superhuman。
> 背景：R300 通知中心 MVP 已交付（五源聚合+动作跳转）；本轮为"已读/分组/静默"深化找增量。

## 1. 各家机制速览

| 产品 | 核心机制 | 对快门可借鉴点 |
|---|---|---|
| GitHub Notifications | 通知按"仓库/原因"分组；Done 列表保留已读可回溯；订阅线程级退订 | **Done 可回溯**：放弃/重试的处置记录保留在恢复中心台账（已有），通知面提供"查看已处置"入口即可 |
| Linear Inbox | Inbox 是**工作队列**而非消息流：每条必须被显式处理（已读/暂存/订阅）；快捷键批处理 | 批处理（全选→放弃/重试）；通知=待处理工作，读后不消失，处理后消失 |
| Grafana Alerting | 告警状态机（firing→resolved）+ 静默窗口（silence）+ 分组聚合标签 | 静默时段（如演示时不打扰）；按 op 分组聚合同类通知 |
| Superhuman | Split inbox：快捷键逐条处理 + 「稍后提醒」 | 逐条快捷键处理（已支持点击）；稍后提醒=低优 |

## 2. 交叉结论（G5-02 深化排序）

1. **通知=工作队列**（Linear 模型）与快门现状最契合：恢复项本就需显式处理（重试/放弃），MVP 已是此模型——方向正确，缺的是**批处理**。
2. **已处置可回溯**：恢复中心台账（resolved.json）已保留处置记录——补一个"查看已处置"筛选入口即达成 GitHub Done 语义。
3. **静默时段/分组聚合**：快门通知量级（个位数）暂不需要——不立项，量级上来再评。

## 3. 立项建议（本轮登记 1 条）

- **R8-A【评估→G5-02】恢复中心批处理**：候选列表支持全选→批量放弃（逐条 markResolved）；验收=10 条候选 3 次交互内清空，台账完整。
