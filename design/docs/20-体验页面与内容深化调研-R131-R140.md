# 体验、页面与内容深化调研 R131~R140：让可信路由器真正可用

> 调研日期：2026-10-02。本轮基于“可信意图路由器 + 小驴生态中枢 + AI 能力层”审查功能、页面、交互、UI 和内容缺口。R73 已覆盖设置页控件、键盘、触控、主题和基础状态；R85/R98 已覆盖意图与上下文合同；R123~R130 已覆盖主线、依赖和门禁。本轮补充用户可见的信息架构、跨页面对象流、恢复中心、AI/动作工作台、内容教育和长期使用体验，不重复定义底层合同。候选登记在 [TODO §19](../TODO.md)。

## 1. 产品体验判断

快门的页面不应让用户先理解 op、MCP、bridge 或插件内部结构。用户首先要看到：我想完成什么、当前需要什么、将会读写什么、现在处于哪一步、完成证据是什么、失败后能怎么办。技术信息应按需展开，且每个页面都能回到原始意图、业务记录或动作 revision。

现有设置页和超级面板属于入口/配置层；还需要补一层“任务与结果工作台”：统一承接来自思源 Agent、Quicker、MCP、面板和快捷键的意图，展示进行中、待确认、未知、已完成和可复用结果。这样快门才是用户能持续依赖的产品，而不只是一次命令的中转站。

## 2. 页面信息架构候选

| 页面/区域 | 用户问题 | 主要对象 | 依赖主线 |
|---|---|---|---|
| 任务首页 | 我现在有哪些未完成事项？ | Intent、待确认、unknown、下一步 | C2/C1 |
| 全局命令/意图入口 | 我想做什么？ | 任务词、上下文、能力候选 | C2/C3 |
| 计划与确认页 | 将要发生什么？ | Plan、目标、字段、风险、确认 TTL | C2/C4 |
| 执行时间线 | 现在进行到哪一步？ | tool call、阶段、耗时、取消 | C1/C4 |
| 结果详情页 | 真的完成了吗？ | Receipt、Evidence、业务实体 | C1 |
| 恢复中心 | 哪些事情需要我处理？ | unknown、冲突、失败、迟到回执 | C1/C4 |
| 能力目录/插件页 | 哪些能力可用？为什么不可用？ | manifest、owner、版本、健康 | C3 |
| AI 工作台 | AI 读了什么、用了什么、如何复用？ | 会话、模板、上下文、评测 | C6 |
| 动作作者工作台 | 如何从目标得到可维护动作？ | ActionSpec、草稿、revision、证据 | C7 |
| 设置/权限/数据页 | 数据去了哪里？如何停止？ | policy、外发、保留、撤销 | C3/C4 |
| 帮助/示例/更新页 | 如何开始和排错？ | 任务配方、术语、版本事实 | C5/C8 |

页面之间必须保留 `intentId`、`planId`、`receiptId`、`actionRevision` 或 `sessionId` 的可点击回链；从通知、诊断和帮助进入时也要保留原上下文。页面数量可以少，但对象关系不能靠用户记忆连接。

## 3. 交互状态和视觉层级

所有高影响操作采用“目标→范围→将读/将写→风险→确认→执行→证据→下一步”的渐进展开。草稿、计划、执行中、等待用户、成功、部分成功、unknown、失败和已撤销使用不同的状态标识与文案；颜色只是辅助，状态文字、图标、时间线和屏幕阅读器语义必须一致。

确认页要能编辑目标和字段，编辑后旧确认失效；执行页要能暂停或取消可取消步骤，显示不可取消副作用；结果页要能打开业务记录、查看证据、继续未完成项、复制脱敏诊断或保存为模板。unknown 必须有“查询原结果”“等待回执”“人工核对”“放弃并记录”四类出口。

## 4. AI 与 Quicker 的用户界面

AI 页面需要把会话、上下文、提示词模板、模型路由、工具轨迹和结果草稿分层呈现。默认显示用户可理解的摘要和证据，调试展开才显示工具名、schema、耗时和模型信息。上下文用可删除的来源 chips 表示，外发字段逐项预览；模板编辑器提供变量来源、输出 schema、拒答条件、工具白名单、fixture 运行和版本差异。

动作作者页面以结果卡开头，逐步展示规格、Quicker AI 草稿、静态审查、暂存差异、试运行、快门回执、业务核验和发布 revision。设计器成功、动作保存、动作试运行和业务完成必须有不同标签。导入/分享页面要先显示最低 Quicker 版本、依赖、权限、脚本和隐私风险。

## 5. 内容与帮助体系

帮助内容按任务组织：快速捕获、全局查找、研究、打卡、人脉、AI 草稿、Quicker 动作创建、失败恢复、升级和卸载。每个配方包含适合谁、输入、结果、时间、权限、失败出口、无 Quicker 替代和可复制示例。术语表解释意图、计划、回执、unknown、owner、能力、暂存、verified 等词，并在 UI 中提供就地链接。

首跑应有角色选择（思源用户、Quicker 用户、AI/MCP 用户、插件作者），但不锁死后续能力；示例工作区和测试数据必须可删除。更新说明按用户结果和迁移影响写，动作/模板/skill/MCP 变更使用同一事实表。错误文案先说发生了什么和下一步，再提供技术详情与诊断复制。

## 6. 深化方向

R131~R140 重点补齐：统一任务首页、跨入口续接、结果和恢复中心、能力/权限可视化、AI 会话和模板工作台、Quicker 作者工作台、帮助与示例、数据生命周期、性能与无障碍、通知和跨设备续接。它们都必须挂在一条真实纵向闭环上，不能脱离用户结果单独堆叠页面。

## 7. 研究门槛

页面候选先做信息架构和可点击原型，再做静态状态检查、键盘/触控/窄屏走查和真实任务观察。至少用“捕获→收件箱→回执”“AI 只读研究”“Quicker 动作草稿”三条路径验证导航、状态、帮助和恢复。没有真实状态数据的页面只做空态和样例，不宣传为已支持能力。

## 8. 当前 UI 静态观察

对实现仓库现有界面做静态核对后，发现设置页仍是单一约 560px 弹窗，设置行主要用普通 `div` 作为视觉标签，控件缺少完整的 label/description 关联；多数配置修改立即保存，缺少待保存、失败回滚和迁移预览。队列、审计、回执和生态信息主要以纯文本弹窗呈现，缺少筛选、排序、加载、空态、复制 ID、深链和长列表处理。

清空队列确认目前不能显示待处理数量、最老项目、将丢弃的 ID、导出后清理和仅清过期选项；异步按钮也需要补 loading、禁用、防抖、取消和竞态保护。未接入主设置入口的 Svelte 辅助标签页已有部分 ARIA 角色，若复用还需补 `aria-controls`、面板关联、方向键/Home/End 导航和焦点回收。辅助表单/对话框库中的 HTML 描述与拼接需在复用前做内容安全审查，多行输入和窄屏布局需要移除不适合的 `nowrap` 约束。全局样式、暗色/高对比/减少动效、移动安全区和大量中文硬编码也需要统一处理。

这些是实现现状证据，不代表本轮已经修复；对应候选已按页面、交互、内容和可访问性拆入 TODO §19。

## 9. UI 原型的范围与层级

本节是文档级原型，不代表当前安装包已经提供这些页面。所有线框内的数量、时间、ID、可用徽章和回执都是脱敏样例，不是真机证据；拾遗当前为未定位能力，首条真实捕获路径须另选已验证目标。原型用于统一信息架构、用户语言和验收顺序，页面回到 intentId、planId、receiptId、actionRevision 或 sessionId。实现前置和修订依据见 [原型落地差距研究](21-UI原型落地差距与实施前置-R141-R150.md)。

原型分三层：

| 层级 | 目标 | 首批验证 |
|---|---|---|
| MVP-1：入口与可观测性 | 让用户知道快门是否可用、有哪些能力、发生了什么 | 首跑/健康、能力目录、队列/回执、设置/诊断 |
| MVP-2：任务闭环 | 让用户完成“意图→计划→确认→结果→恢复” | 任务首页、意图编辑、计划确认、执行时间线、恢复中心 |
| MVP-3：作者与 AI | 让用户安全地复用 AI 和 Quicker 产物 | AI 工作台、上下文检查、提示词模板、动作作者链、发布预检 |

每页都必须设计 loading、empty、error、unknown、partial、权限不足和能力缺席状态；状态更新不能丢失焦点、筛选、滚动位置或返回来源。

顶层导航候选为：


## 13. 意图编辑与计划确认

意图编辑器把自然语言和结构化字段放在同一页面，避免用户在协议字段和自然语言之间来回切换。

~~~text
┌─ 新建任务：保存到收件箱 ────────────────────────────────────┐
│ 我想做什么？ [把刚才选中的内容保存到收件箱                 ] │
│                                                              │
│ 上下文                                                         │
│ [当前选区 ×] [项目笔记 ×] [来源时间 10:31 ×]  [+ 添加来源]   │
│ 新鲜度：刚刚       敏感级别：普通       外发：不发送          │
│                                                              │
│ 识别结果                                                     │
│ 目标：创建收件箱块      范围：1 个选区      owner：目标能力（样例）       │
│                                                              │
│ [生成计划]                              [保存草稿] [取消]      │
└──────────────────────────────────────────────────────────────┘
~~~

计划确认页：

~~~text
┌─ 执行前确认：保存到收件箱 ──────────────────────────────────┐
│ 这次会发生什么                                               │
│ 1. 读取：当前选区（12 行）                                  │
│ 2. 写入：收件箱，创建 1 个块                                │
│ 3. 外发：无                                                  │
│ 影响：创建 1 个块  恢复能力：待核对  耗时：尚未测量          │
│                                                              │
│ 参数 diff：目标收件箱 [默认] → [收件箱]                      │
│ 有效期：本次执行       幂等键：自动生成                       │
│                                                              │
│ [展开技术详情]       [返回修改] [保存计划草稿] [确认并执行]     │
└──────────────────────────────────────────────────────────────┘
~~~

修改目标、范围、字段或权限后，失效范围由统一 Confirmation 合同决定；当前整份一次性确认应重新生成计划并整体确认，局部确认须先有合同与 owner 证据。读确认不能自动升级为写确认。保存草稿不保存旧授权，重启或过期后必须重新检查能力与上下文再生成计划。一次性执行、预约、重复规则和后台自动化使用不同入口和文案。

## 14. 执行、结果与恢复中心

执行时间线：

~~~text
┌─ 保存到收件箱 · 执行中 ──────────────────────────────────────┐
│ intent 8f2…   plan p31…   来源：Quicker   停止后续（需能力）   │
│ ✓ 已读取选区                         10:31:04   120 ms       │
│ ● 正在调用目标能力（样例）                    10:31:04   …            │
│ ○ 等待业务回执                                               │
│                                                              │
│ 取消条件由 owner 声明；未声明时仅退出观察，不承诺停止写入           │
└──────────────────────────────────────────────────────────────┘
~~~

结果卡先展示用户结果，再展示证据和协议：

~~~text
┌─ 任务结果：保存到收件箱 ─────────────── verified ● ──────────┐
│ 已创建 1 个收件箱块，10:31:05                               │
│ [打开块] [复制链接] [复用这条任务] [反馈结果]                 │
│                                                              │
│ 证据：目标能力回执 r91…（样例）   业务时间 10:31:05   数据截至 10:31:05    │
│ 详情 ▸ 读取范围、写入字段、耗时、动作 revision                 │
└──────────────────────────────────────────────────────────────┘
~~~

恢复中心统一收纳 unknown、partial、failed、迟到回执、目标删除、插件卸载和版本冲突：

~~~text
┌─ 需要处理 ───────────────────────────────────────────────────┐
│ unknown  联系人互动       需确认是否已经写入        [查原结果] │
│ partial  批量保存 3/5     2 项未完成                [选择重试] │
│ failed   收件箱不可用     目标插件未初始化          [看修复]   │
│                                                              │
│ 四类候选路径（按 owner 能力与权限确定可用性）：                                        │
│ [查询原回执] [等待回执] [人工核对] [放弃并记录]                │
└──────────────────────────────────────────────────────────────┘
~~~

“放弃并记录”只关闭用户跟进，不改变未知业务事实；必须保存理由、时间和来源，并保留迟到回执入口。查询、重试、补偿和撤销根据 owner 公开能力显示可用条件，缺接口时给人工路径；危险动作先显示副作用、幂等键和影响范围。

## 15. 能力、权限与诊断页

能力目录以用户结果分组，而不是按原始操作名罗列：

~~~text
┌─ 能力 ───────────────────────────────────────────────────────┐
│ [全部] [可用] [需配置] [只读] [实验]       搜索能力、插件…     │
│ ┌──────────────────────────────────────────────────────────┐ │
│ │ 保存到收件箱                         样例可用 · 目标待验证            │ │
│ │ 读取当前选区 · 写入 1 个块 · 不外发                         │ │
│ │ 最近验证：今天 10:31   替代：复制为纯文本                   │ │
│ │ [试用] [查看权限] [查看回执]                                │ │
│ └──────────────────────────────────────────────────────────┘ │
│ ┌──────────────────────────────────────────────────────────┐ │
│ │ 查询今日打卡                         需配置 · 打卡          │ │
│ │ 原因：插件未初始化；不会显示为空                           │ │
│ │ [去配置] [查看诊断]                                         │ │
│ └──────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────┘
~~~

权限页按字段展示“将读、将写、外发服务、保留期限、撤销方式”。诊断向导固定为“探测 → 解释 → 修复 → 复测”，修复前列影响，修复后保存证据。清空队列前显示数量、最老时间和将丢弃的 ID，并支持导出后清理和仅清过期。

~~~text
│ 未知：……                                                     │
│ 建议：保存为草稿 / 继续询问 / 转人工                          │
│                                                              │
│ [重新生成] [编辑草稿] [接受为计划] [拒绝] [停止]               │
└──────────────────────────────────────────────────────────────┘
~~~

模板编辑器显示变量来源、输出 schema、拒答条件、工具白名单、渲染前后 diff 和 fixture 结果。沙盒试跑禁止真实工具；无模型时提供手动模板、只读查询和保存原文入口。

## 17. Quicker 动作作者工作台

~~~text
┌─ 动作作者：保存到收件箱 ─────────────────────────────────────┐
│ 1 规格  →  2 AI 草稿  →  3 静态审查  →  4 暂存               │
│ → 5 试运行 → 6 业务核验 → 7 revision / 分享                 │
│                                                              │
│ 目标：选区内容进入收件箱                                    │
│ 输入/输出：selection → receipt                               │
│ 依赖：Quicker V2、快门、已验证目标；权限：读选区、写目标           │
│                                                              │
│ 审查结果：2 个提醒、0 个阻断                                │
│ [查看模块 diff] [查看 Token/路径脱敏] [交接到 Quicker（方式待验证）]    │
│ [试运行] [回到旧 revision] [保存草稿]                         │
└──────────────────────────────────────────────────────────────┘
~~~

作者页面必须区分“设计器成功、动作保存、动作试运行、业务完成”四种状态；设计器助手要求 Quicker 2.2.25 起，运行分析要求 2.2.26 起，本机暂存不代表跨设备同步。打开暂存、导入和读取编辑结果分别需要公开交接接口证据，未验证时只提供导出/复制和人工步骤；导入和分享前预览最低版本、依赖、权限、脚本、Token、正文、截图、日志和许可。Quicker 运行分析只能生成建议，不能单独把业务状态标为 verified。

## 18. 设置、隐私与通知

设置页按“连接与工作区、能力与权限、AI 与外发、数据保留、通知、诊断”分组，支持搜索、高级项折叠、待保存提示、失败回滚和迁移预览。每个字段必须有可关联的 label、说明、单位、范围和错误信息。

通知中心统一待确认、需恢复、成功、提醒和安全告警，支持去重、合并、静默时段、低动效、复制诊断和深链。通知关闭不等于停止业务执行；权限回收、Token 变化、异常外发和被阻断的排队任务进入可追溯安全通知。

## 19. 三条原型验收路径

| 路径 | 需要证明的用户结果 | 必查状态 |
|---|---|---|
| 捕获 → 收件箱 → 回执 → 核验 | 用户能确认范围，并从结果打开业务块 | loading、确认失效、verified、unknown、恢复 |
| AI 只读研究 → 草稿 | 用户知道读取和外发了什么，能拒绝写入 | 上下文删除、模型不可用、引用缺失、schema 错误 |
| Quicker 动作草稿 → 试运行 → 业务核验 | 作者能区分动作保存和业务完成 | 依赖缺失、静态阻断、试运行取消、partial、revision 回退 |

每条路径均需检查：键盘和读屏顺序、中文输入法、320px 窄屏、200% 缩放、暗色/高对比、减少动效、返回来源、深链失效和脱敏诊断。

## 20. 文案和状态词规范

首句先说明发生了什么，第二句说明影响，第三句给下一步；技术详情最后展开。下面是展示词汇，不是一条完整线性状态机：任务阶段、执行事实、证据核验和人工处理须分开投影到 C1，旧 recorded/duplicate 不能直接成为 verified，放弃/已读不改写业务事实。规范和映射见 [状态模型约束](21-UI原型落地差距与实施前置-R141-R150.md)。

~~~text
draft                 草稿
planned               已生成计划
awaiting-confirmation 待确认
running               执行中
committed             已提交
verified              已核验
partial               部分完成
unknown               未知，等待或需要核对
failed                失败
cancelled             已取消
expired               已过期
rejected              已拒绝
~~~

颜色只做辅助，状态文字、图标、时间线和屏幕阅读器语义必须一致。文案不得把“没有权限”“插件未初始化”“连接不可达”和“确实没有数据”写成同一个空态。

## 21. 与待办和实现证据的关系

本原型对应 [TODO §19](../TODO.md) 的 R131~R140，新增事项仍处于调研和评估阶段。当前实现只有设置、桥/诊断和协议相关界面，尚未提供任务、结果、AI 或动作作者工作台；静态观察记录在本文件第 8 节，具体证据包括：

这些缺口用于指导原型评审和后续待办验收，本轮不修改实现。新增前置见 [TODO §20](../TODO.md) 和 [R141~R150 研究](21-UI原型落地差距与实施前置-R141-R150.md)，已覆盖的状态、安全、无障碍等总项只细化验收。
