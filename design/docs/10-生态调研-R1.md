## 3.7 R7 循环A：雷切 0.44 三新能力评估（2026-10-02，design note）

雷切远端 main（0.44.1）新增能力对照中枢纪律（只消费公开能力、不重复造）逐项评估：

| 新能力 | 是什么 | 评估结论 |
|---|---|---|
| `get-document-outline` | 文档大纲只读查询（上限 48 项） | **不接入**。内核 SQL（`blocks WHERE type='h' AND root_id=…`）已覆盖大纲查询，且快门超级面板"大纲跳转"直接走内核即可，绕道雷切反而加依赖。 manifests 保留登记（registry.list 可见）即可 |
| `home-adapter-diagnostics` | 雷切 home 组件适配器诊断（backoff/cache/timeout 等） | **不接入**。跨插件健康口径已由 `diagnostics.report`（快门自身）+ `registry.list`（各插件 installedVersion/installed）覆盖；雷切内部诊断属其私有运维面，中枢不消费 |
| `restore-document-set` | 批量恢复一组文档（工作区快照还原，带确认） | **接入=零成本**。经既有 `commands.run` 机制调用雷切命令面板条目即可（确认语义由雷切自身承担）；docs/03 方向二「窗口布局保存/恢复」行已标注该能力名。晨间启动/会议模式编排（docs/03 §2）可直接编排它 |

**总结**：0.44 新能力无需新增任何 op 或适配器——read 类内核已覆盖、诊断类不该消费、action 类走既有 commands.run。这正是"成熟度矩阵 + commands.run 兜底"设计预期的验证。

## 3.12 R11 循环C：Drafts「捕获→分拣→分发」范式（2026-10-02）

[Drafts](https://getdrafts.com)（iOS/macOS 快捕标杆）的核心哲学：**先捕获（打开即空白页）→ 中转收件箱 → 事后分拣分发**（[收件箱处理实践](https://forums.getdrafts.com/t/best-practices-for-processing-my-drafts-inbox/10966)、[社区分拣动作](https://actions.getdrafts.com/a/1ch)：逐条询问去向）。

**对本项目**：现有 P0-1（直落日记）/P0-2（落入收集箱）都是"捕获即分发"，缺 **分拣端**——收集箱会只进不出。Drafts 模式提示补一个 **SY·分拣收集箱** 动作：列出收集箱未处理块 → 逐条（或批量）选去向（移入今日日记 / 转待办 / 记人脉互动 / 删除）→ `moveBlock`/`deleteBlock`。纯内核 op 可实现，与 P0-2 构成闭环。已补进 docs/03 方向二扩展目录（R11）。

**结论：值得做，列为 M3 首项；前置=内核重启复测批通过。**

**价值面**（R8 §3.9 差异化框架的落地化）：Sisyphus 已验证"AI 助手经 MCP 读写思源"有真实需求，但其工具面只覆盖内核 CRUD；快门 MCP 化的增量=**小驴生态 op 面**（commands.run 触发任意思源命令、checkin.record/summary、contacts.search/interaction、events.list/pull、workflow.plan/execute、config.discover、registry.list、diagnostics.report）——AI 助手可直接"帮我打个卡""记一笔人脉互动""跑一遍汇总工作流"，这是任何现有 SiYuan MCP Server 都没有的能力面。

**技术路径三选一**：

| 路径 | 说明 | 结论 |
|---|---|---|
| kernel.js 内实现 MCP over HTTP | 复用私有路由模式 | ❌ Claude Desktop 主流走 stdio，内核内实现受制于思源 HTTP 服务器语义，且升级随插件绑定 |
| **独立 stdio 代理进程** | `@lv/mcp-quickgate` npm 包：MCP stdio ↔ 内核 HTTP API（复用 lv-cli 的 send/receipt/fast 全套逻辑） | ✅ **推荐**：零插件改动、独立发版、Claude Desktop/Cursor 即插即用；23 op 一比一映射 MCP tools；可用官方 `@modelcontextprotocol/sdk`，预估 1~2 天 |
| Quicker 侧桥接 | MCP for Quicker | ❌ MCP 消费方是 AI 客户端，与 Quicker 无关（Quicker 走既有三通道） |

**安全模型**（复用快门既有红线延伸）：MCP tools 元数据标注 `readOnlyHint`/`destructiveHint`（registry.list/diagnostics/events/checkin.summary/config.discover=只读；commands.run/record/interaction/workflow.execute=写/副作用）；**代理默认只暴露只读 op**，写 op 需设置页显式开启 `mcpWriteEnabled`（对齐 plugin.api 允许名单模式）；黑名单/确认门控/审计全共用——MCP 只是又一个消费通道，不新增特权。

**验收形态**：Claude Desktop 配置一条 stdio server → "用小驴帮我记一条今天见了某人" → checkin/contacts 调用 → 回执可读。与 Sisyphus 可并存（不同工具前缀）。

## 3.15 R39：R8 立项 ②③ 评估结论（2026-10-02）

**② 笔记本级写权限分级（借鉴 Sisyphus none/r/rw/rwd）→ 暂不立项，理由记录：**

**③ doc.resolve（hpath→块 ID 便利 op）→ 保持备选池，理由记录：**

- 两条既有路径已覆盖：SQL `SELECT id FROM blocks WHERE type='d' AND hpath='…'`（workflow 步骤可直接用）；`listDocsByPath`（kernel 已空值防护，返回 id）

## 3.23 R77：小驴系列插件联动的产品化调研（2026-10-02）

联动应按用户任务验证，不按“已经有几个 adapter”宣传。候选主线为：晨间启动（雷切上下文/布局→今日日记→打卡待办→昨日未完）；快速捕获（拾遗/收集箱→来源与时间→分拣→日记/任务/人脉）；会议（模板→计时→联系人互动→行动项）；阅读学习（网页/PDF/视频摘录→拾遗→闪卡→考试复习）；晚间复盘（日记/打卡/人脉→汇总→次日行动）。

每条主线必须标明能力来源、输入/输出文档、数据权属、前置插件、可跳过步骤、部分失败后的继续点和最终回执；缺少某个插件时保留可执行的子流程并解释替代路径。跨插件事件需要统一名称、版本协商、source、correlation/idempotency key、删除和保留策略；结果页显示来自哪个插件、哪个版本、何时产生以及原记录是否仍可定位。

## 3.24 R77：插件清单与联动事实核查（2026-10-02）

这轮把快门的 `src/assets/ecosystem-manifests.json` 与本地插件源码、公开契约逐项对照，发现“有目录项”不等于“可调用”。当前清单把闪卡写成 `siyuan-flashcards`/v0.5.0，本地 `plugin.json` 是 `siyuan-lv-cards`/v0.63.0；考试清单 v0.1.0，本地 v0.5.1；拾遗写成 `siyuan-shiyi`/unlocated，本地仓库已定位为 `siyuan-glean`/v1.1.0。以上是本机 checkout 快照，不能直接称为远端最新发布。人脉还存在本地 checkout 与远端版本不同步，校准时必须记录 remote/local commit 和时间，不能只比较某个旧工作区文件。

| 模块 | 当前可核验事实 | 产品边界 |
|---|---|---|
| 打卡 | `window.siyuanCheckin` v5，具备 read/record 和公开事件 | 可进入稳定联动；记录 source 和 session/externalRef |
| 人脉 | `window.LvContacts` v1，search/get/ensure/recordInteraction | 可进入稳定联动；严格校验 protocol/capabilities 和重名 |
| 雷切 | `window.siyuanSpeedSwitch`、Agent/commands/home provider | 负责导航、上下文和命令，不成为业务数据真相 |
| 拾遗 | 设计态 `window.siyuanGlean`，仓库有数据契约但公共桥未挂载 | 未公开前只能保留原摘录，不能宣传读库联动 |
| 闪卡 | 通过 eventBus 发 reviewed/session-finished/streak-changed/gateway-changed，cards-created 预留 | 缺稳定 session 协议和持久事件载体前不接入默认工作流 |
| 考试 | 只有一次性 `lv-exam:stats` CustomEvent，无版本化公共 query bridge | 不能由一次 stats 推导正式完成和学习打卡 |

因此联动待办要先校准 ID、版本、能力、事件 ingestion 和 source of truth，再设计晨间、会议、知识输入、复习、晚间总结等产品流。每条流都要处理缺插件、版本不兼容、单源超时、事件重复、部分成功、跨设备回放和原记录删除；中枢只做编排、回执和解释，不读取业务插件私有库或自行重算业务口径。

## 3.25 R75：配置、数据生命周期与多工作区调研（2026-10-02）

配置体验应围绕用户能理解的数据边界：哪些属于工作区、哪些属于设备、哪些可能同步、哪些包含敏感信息、升级后怎样迁移。当前导出设置和 normalize 只提供底层能力，尚缺 schemaVersion、差异预览、选择性导入、分层重置、迁移报告和回退路径。processed 台账迁移与普通 UI 设置迁移必须分开评估，清空前者会改变重复执行风险。
