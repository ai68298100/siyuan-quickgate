# 协议 v2 候选评估：按写者分文件（L453 遗留 · R236 design note）

> 问题：多生产者并发追加 commands.ndjson 的互覆竞态，R232 已用「写后读回校验+重试」缓解（实测 0 丢失，代价=重复行+至多 5 次重试）。本 note 评估是否值得升级协议 v2（每写者独立命令文件）。
> 裁定：**暂不立项**；触发条件见 §3。

## 1. 现状（v1.1 + R232 缓解后）

| 维度 | 现状 |
|---|---|
| 正确性 | 实测 0 丢失（写者自身行保证落盘）；重复行由 processed 台账按 id 去重 |
| 延迟 | 无争抢时零额外开销；争抢时每次重试 ≈3 次 HTTP（~100ms 级），上限 5 次 |
| 复杂度 | 三个内置客户端各 ~10 行；协议信封/消费者零改动 |
| 残余风险 | 最后一次写竞态（写者 A 验证后、写者 B 基于旧快照覆盖——A 的行丢失且 A 已返回成功）；理论上界=并发写者数的最后一步窗口 |

## 2. v2 方案（按写者分文件）的代价

1. 消费者：tick 需枚举 `commands-*.ndjson` 多文件（SiYuan 文件 API 无 list——需维护写者注册表或约定文件名集合，**这是最大障碍**：无目录列举原语）；
2. 契约：信封/文件布局/压缩语义/docs/02 五处升级，所有外部客户端（含用户自写脚本）迁移；
3. 收益：消灭最后写竞态 + 免重试延迟。

## 3. 触发条件（满足其一再立项）

1. 真实场景出现「≥4 个常驻写者 + 高频（秒级）并发」且读回重试的可观测失败（客户端抛「重试 5 次未持久化」日志出现）；
2. 思源文件 API 提供目录列举（消除注册表障碍）；
3. 广播通道已承载高频写且 SSE 断连频发（说明 NDJSON 并发需求真实上升）。
