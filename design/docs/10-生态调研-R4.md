## 2. 与快门的对照修正（L561 矩阵第三行改写）

此前口径「思源原生 MCP=竞品」**不完整**：

| 场景 | 关系 |

| 内置 MCP 服务器（思源自带 tools） | 重叠面=思源原生操作；**不重叠**=小驴生态透传/工作流/收藏/模板 |

## 6. 追加（R252）：Agent 侧审批语义（decision.go/capability.go 源码实证）

- 内置 Agent 对能力调用的授权 = **用户可配置的按能力审批策略**：`Conf.AI.Agent.ApprovalPolicy.Decision(capabilityID, action)`，未配置时缺省 `ApprovalDecisionRisk`（按风险分级）。
- 快门注册能力时声明的 **effects（localRead/localWrite）正是风险判定输入**——申报不实会被策略放行/拦截错配，R245 的如实声明因此有安全意义。
- decision.go 的「决策模型」（可选 LLM 辅助判定）被规范为**证据而非授权**：不得把权限委托给决策模型——与快门「防线在 dispatch 层」同构。

→ R244-A 接入指南的 Agent 侧预期：能力注册后，用户在思源 AI 设置的审批策略里按能力 ID（plugin__siyuan-quickgate__*）配置 放行/询问/拒绝；effects 声明决定缺省风险档。

## 7. 追加（R257）：全新工作区内核插件启用的三条确凿知识（沙箱实验副产品）

用 `SiYuan-Kernel.exe serve --workspace <临时>` 做干净沙箱验证时源码+实验实证（工具=tools/clean-sandbox.mjs，实验态）：
1. **全新工作区默认禁用内核插件**：`IsPetalsEnabled` 要求 `Conf.Bazaar.Trust=true` 且 `PetalDisabled=false`（桌面/Docker 还要求用户手动确认信任）——petal 启用状态持久化于 `data/storage/petal/petals.json`（SetPetalEnabled→savePetals0）。
2. **首跑持久化会自动开启本地 TLS**（cert.go 生成本地 CA）——无头探针需显式 `system.networkServeTLS=false` 或走 https 自签容错。
3. 遗留：二启在数据库重初始化后挂起（机制级，无插件也复现，与快门无关）——沙箱路线暂停，续做线索在工具头注。

## 8. 追加（R263）：getFile 对插件存储的可见性规则（真机实证）

- `/storage/petal/<插件>/bridge/*`（桥公开载体）→ getFile **放行**（200）；
- `<插件>/audit.json` 等前端 `saveData` 写的**非 bridge 文件** → getFile **202 隐藏**（即使带有效 Token）——内核在 API 层执行「插件私有存储不暴露」；
- 推论：审计/设置类私有状态的真机检查走设置页 UI（前端进程内直读），不走 getFile；桥载体文件与 favorites.json（经内核 putFile 写入）保持 API 可见。
