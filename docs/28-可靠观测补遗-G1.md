# 可靠性与可观测性补遗（G1 · §18.6 R128 · v0 规格）

> 目的：R128 七条对照已实现机制的盘点——**五条已有归宿（引用既有合同/工具），两条需要新建**（outbox 补偿、SLO 基线测量）。
> 状态：v0 规格——planned 项全部登记 TODO，不在本合同承诺实现。

## 1. 分布式追踪（R128 第一条）

关联字段链 `intentId → planId → commandId → receiptId → 业务实体/动作 revision`：

| 段 | 现状 |
|---|---|
| commandId → receiptId | ✅ 已实现（信封 id 贯穿三通道+审计+results.ndjson） |
| planId → commandId | ✅ workflow.execute 按计划派生命令（planId 记于审计上下文） |
| intentId | ⬜ planned——依赖 C2 Intent 中枢（R116）；近期以"动作 revision + 命令 id"作弱关联 |
| 业务实体 | 部分可查（checkin/contacts 回执带实体 id；块写入带块 id） |

**缺口登记**：intentId 贯穿（R116 一并设计）；跨通道关联查询 UI（planned，依赖台账导出）。

## 2. unknown 主线（R128 第二条）✅ 已有归宿

同 ID 查询/补回执路径 = result-contract §1（timeout=unknown 语义）+ §3（先查后补救）+ lv-cli `receipt --id`。插件卸载/进程退出的迟到结果按 `duplicate` 收敛（台账）。**不伪装**不变量已入合同。

## 3. 写入 outbox（R128 第三条）⬜ 评估结论：暂缓

当前写入面窄（template.new/appendBlock 直呼内核），且台账+回执窗口已覆盖"空洞"可见性。**触发条件**（登记）：出现"多步业务写入"（如 workflow 跨 op 事务）或桥目录迁移（D-0006）时，再引入 outbox/补偿记录。现在引入=为不存在的写入量设计。

## 4. 取消语义（R128 第四条）——逐项标记

| 环节 | 可取消？ | 已发生副作用与迟到可能 |
|---|---|---|
| 确认窗等待 | ✅（超时/拒绝=取消） | 无副作用 |
| 网络请求（内核 API） | ⚠️ 客户端 abort 即放弃等待，内核可能已完成 → **迟到回执可能** | 查询 results 按 id 收敛 |
| 脚本执行（Quicker C#） | ❌ 不可取消 | 运行完为止；幂等由 id 派生 externalRef 兜底 |
| 业务写入（appendBlock/recordEvent） | ❌ 已写入即成事实 | 回执如实记录；删除属业务操作（手动） |
| workflow 计划 | ✅ 未执行计划过期作废（5min TTL）；**执行中不可暂停**（planned：workflow.cancel，见 C4 §3） | stoppedAt 起后续步骤未发生 |
