# Quicker 动作作者链（G4 · §18.5 R127 · v0 规格）

> 目的：把 AI 写动作、蓝图（§2/§3）、动作结果卡（R106~R113）、提示词体系（R122）收敛为一条 **Action Lifecycle**；验收 = 每个动作只维护一份生命周期。
> 状态：v0 规格——绑定 G2 样板首成功之后实施；本规格即"搭样板"时的操作规范本身。

## 1. Action Lifecycle 六态

```
①结果卡 → ②骨架（AI/手工） → ③静态门禁 → ④暂存试运行 → ⑤正式化 → ⑥业务 verified →（维护循环/退出）
```

| 态 | 进入条件 | 产出 | 唯一存放处 |
|---|---|---|---|
| ① 结果卡 | 创建**前**强制 | docs/25 §3 同款九项（用户结果/输入输出/目标窗口/权限/副作用/证据/回执/手动替代/下一步） | docs/25 §3 模板，每动作一份 |
| ② 骨架 | 结果卡评审过 | AI 写动作（附A 提示词）或手工搭的 .qa 骨架 | quicker-actions/ 工作目录 |
| ③ 静态门禁 | 骨架导入后 | 门禁清单全过（§3） | 检查记录随动作归档 |
| ④ 暂存试运行 | 门禁过 | 真机试运行记录（正常+异常样例各一） | §6 样例表打勾 |
| ⑤ 正式化 | 试运行过 | .qa 导出入 quicker-actions/ 登记 | 归档表 |
| ⑥ 业务 verified | 真实使用 ≥1 周（G2-最小可用同标准） | 结果卡"verified"标记 + 证据 | 结果卡 |

**验收（R127 第一条）**：每个动作只维护一份生命周期文档——蓝图、AI 提示词输出、试运行记录全部指向同一份，不并存副本。

## 2. 结果卡前置（R127 第二条）

"帮我做一个动作"**不得直接进入生成**——AI 提示词（附A）的第一段改为要求模型先产出结果卡草稿，用户确认结果卡后才生成骨架。结果卡九项沿用 docs/25 §3（用户结果/输入/输出/目标窗口/权限/副作用/证据/手动替代/下一步）。

## 3. 静态门禁清单（R127 第三条：单一检查器，不重复实现）

| # | 检查 | 依据 |
|---|---|---|
| 1 | ActionItem2/V1-V2 兼容 | Quicker V2 文档 |
| 2 | 变量拼写与定义齐全 | 蓝图变量表 |
| 3 | 模块依赖（HTTP/文件/模拟输入权限） | Quicker 权限模型 |
| 4 | C# 脚本语法 | csc/Roslyn 可先验（R33 方法） |
| 5 | 网络目标 = SY_URL（6806 默认）| 端口地雷教训（R56） |
| 6 | Token 不入包（导出前扫 token 形状） | 凭据卫生（R63） |
| 7 | 版本与 quicker-actions 登记一致 | 归档表 |

实施形态 `planned`：一个 validate-action.mjs（对 .qa 包解包检查）——单一工具承担全部检查；不逐条写散脚本。

## 4. 五态区分与业务核验（R127 第四条）

`AI 生成 / 设计器保存 / 试运行通过 / 正式化导出 / 业务 verified` 是五个不同状态：
- Quicker 导出成功 ≠ 试运行通过；试运行通过 ≠ 业务 verified（result-contract：HTTP 成功≠业务完成）。
- **唯一业务 verified 证据 = 快门回执/内核查询命中**（样板的 SQL 回查模式，result-contract C1）。

## 5. 作者证据（R127 第五条）

每动作 revision 记录：生成用 prompt+model（若有 AI 参与工具 schema）、静态门禁结果、试运行样例、失败恢复验证、兼容矩阵行（思源×Quicker×Windows）。分享包（.qa+README）能复现来源——即 release-evidence-contract 的动作级缩微版。

## 6. 退出（R127 第六条）

模块/权限/回执/维护成本任一门槛不满足 → 动作保留草稿态（不删，进 `quicker-actions/drafts/`）或撤销发布（从归档表移除）——**不可维护的动作不进稳定目录**（reliability-contract 的"AI 场景可以有尊严地死掉"同款纪律）。
