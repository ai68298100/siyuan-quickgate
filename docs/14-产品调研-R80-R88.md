## 2. R80：知识捕获后的维护、关联和复用

Zotero 将集合、标签和关联作为不同的组织方式：同一条目可属于多个集合；关联可表达版本、系列、评论和资料之间的关系。关联是双向、非传递且限于同一库。因此，本项目的专题资料篮应优先引用原记录；“相关”“支持”“反例”“前置知识”“修订版”需要明确语义，不能按相似度自动合并。[Zotero 集合与标签](https://www.zotero.org/support/collections_and_tags)、[Related Items](https://www.zotero.org/support/related)。

Obsidian 反链把已链接和未链接提及分开，并展示上下文。这为处理历史笔记里的人物/概念提供参照：候选提及应受别名、范围和排除项控制，用户逐项确认；从旧内容发现提及与捕获时识别人名是两个不同的任务。[Obsidian Backlinks](https://help.obsidian.md/plugins/backlinks)。

Readwise 允许调节资料/类别的回顾频率，其文档也明确质量过滤可能把汉字短句误认作残缺句。这揭示两个独立问题：用户需要知道资料为何重浮、如何降低频率；质量提示不能仅靠字符长度，更不能自动删除内容。相关候选通过拾遗公开能力执行，快门只展示原因和引导。[Readwise Reviewing Highlights](https://docs.readwise.io/readwise/docs/faqs/reviewing-highlights)。

本项目的新增设计假设：把原文、自己的注释和推断分开；围绕研究问题组织主张、支持证据、反例和待确认项；源版本变化后提示引用和衍生卡题复核；记录摘录实际用于哪个项目/输出。以上是从产品机制推导的候选，不是现有快门功能。

## 3. R81：内容导入、更新和迁移的真实边界

Readwise 的新高亮会追加到已导出的笔记，但既有高亮的修改不会自动传播，以避免覆盖目标笔记里的用户编辑。这说明“一次导入成功”之外还要定义外部字段、本地注释、删除、冲突和再次导入的所有权。拟先评估用户主动文件导入；服务 API 同步属于另一个需授权、配额和失败恢复的候选。[Readwise Exporting Highlights](https://docs.readwise.io/readwise/docs/exporting-highlights)。

Zotero 的重复合并与简单删除不同：合并需要保留集合、标签和引用联系。PDF 批注还可能存于数据库而非原 PDF，单独复制 PDF 不等于携带批注。本项目应显示支持格式、字段映射、附件/批注是否包含、合并后引用去向和导出损失；通过公开接口或用户提供文件处理，不读取第三方私有数据库。[Zotero Duplicate Detection](https://www.zotero.org/support/duplicate_detection)、[Annotations in Database](https://www.zotero.org/support/kb/annotations_in_database)。

Anki 文本导入区分字段映射、重复和更新身份，更新内容与学习调度是不同责任。现有远期“2Anki 通道”需要细化为稳定外部身份、更新预览、牌组策略、历史保留和往返样本；不能让一次内容导出重置已学习卡片。[Anki Text File Import](https://docs.ankiweb.net/importing/text-files.html)。

## 4. R82：工作流产品管理与一次性执行的差别

当前 `src/services/workflow.ts` 是一次性内存计划：最多 8 步、5 分钟过期、固定 args、顺序执行、一次总确认、失败停止；没有已实现的条件分支、输出变量映射、长期规则库或后台触发器。因此，新的自动化管理事项先评估产品职责，不能通过扩白名单或 `plugin.api` 代替设计。

参照现成编排产品时，重点研究草稿与发布版本、手动/事件/定时执行、输入输出契约、测试样本与真实数据、条件模拟、执行历史、暂停、冷却、运行限额、回环保护和规则变更。规则重放必须同时说明旧版本输入与新版本定义的区别，已发生副作用的步骤不能默认重新运行。此处的参数映射、规则管理和触发能力均是候选，后续先判断由 Quicker 或其他现成工具承担还是快门需要新增最小能力。

| 官方参照 | 文档明确的机制 | 本项目的设计推导 |
|---|---|---|
| n8n 执行/发布 | 手动与生产执行分开；生产使用发布版本 | 测试许可不能自动转为无人值守写许可，编辑不能静默改变正在执行的定义 |
| n8n 历史/固定数据 | 历史执行可按原版或当前版重试；测试可以固定样例 | 原结果查询、原版重放、新版处理分开；模拟不能派发真实写 op |
| Node-RED 消息/上下文/错误 | 消息有身份；上下文有节点/流程/全局范围；错误带来源与回环保护 | 运行变量隔离、因果链、最大传播深度、连续失败熔断 |
| Apple 自动化 | 自动化可暂时停用；同步后的个人自动化默认禁用 | 规则模板和本设备自动运行授权分离，换机后先复核再启用 |

来源：[n8n 执行类型](https://docs.n8n.io/build/understand-workflows/understand-executions/types-of-executions)、[保存与发布](https://docs.n8n.io/build/understand-workflows/save-and-publish-workflows)、[执行历史](https://docs.n8n.io/build/understand-workflows/understand-executions/view-all-executions)、[固定/模拟数据](https://docs.n8n.io/build/work-with-data/pin-and-mock-data)、[数据映射](https://docs.n8n.io/build/work-with-data/reference-data/use-the-ui-mapper)、[并发控制](https://docs.n8n.io/deploy/host-n8n/configure-n8n/scaling/control-concurrency)、[Node-RED 消息](https://nodered.org/docs/user-guide/messages)、[上下文](https://nodered.org/docs/user-guide/context)、[错误处理](https://nodered.org/docs/user-guide/handling-errors)、[Apple 快捷指令同步](https://support.apple.com/guide/shortcuts/sync-shortcuts-apdb3a4240b0/ios)。本轮核查时 n8n 旧 `/workflows/...` 路径已不可用，记录使用当前 `/build/...` 路径。

## 5. R83：离线草稿、迟到命令和跨设备接力

Joplin 将本地保存与跨设备同步分开；冲突处理保留可比较的副本，用户可以决定合并。它的浏览器版还说明浏览器本地数据清除可能删除尚未同步的内容。因此，快门客户端需要区分“已保存草稿”“待执行命令”“已写入但未收到回执”和“同步已完成”，不能用一个绿灯表达四种状态。[Joplin 同步机制](https://joplinapp.org/help/dev/spec/sync)、[冲突处理](https://joplinapp.org/help/apps/conflict/)、[Web 本地存储](https://joplinapp.org/help/apps/web/)。

拟验证三种中断：电脑思源未运行、手机无法接触电脑、外网断开但本地 Kernel 可用。前两种可评估用户主动保留客户端草稿；第三种不应强迫等待云服务。离线内容恢复需要用户复核日期、目标、来源设备和当前文档版本，不能自动把过期命令补写到今日。

跨端接力先研究用户明确选择的一份内容、其来源身份和处理状态；设备同步不是外部写命令传输协议。附件可读性、工作区目标、时区、恢复批次和冲突预览均需验收；只通过思源公开能力或人工操作处理冲突，不改写内部同步实现。

## 6. R84：学习、人脉、项目与打卡的深层场景

Anki 对难卡建议修改呈现方式、拆分、补理解或暂缓；过滤牌组则支持限定范围的临时复习并有自己的调度语义。这为“复习完成后打卡”之外的学习质量闭环提供参照：困难项→来源→修订→重新练习；回答次数、独立卡数、保留率和预计负担分开呈现，口径由学习 owner 提供。[Anki Leeches](https://docs.ankiweb.net/leeches.html)、[Filtered Decks](https://docs.ankiweb.net/filtered-decks.html)、[Statistics](https://docs.ankiweb.net/stats.html)。

Monica 将日记与人物、活动关联，启发会前回顾、互动中的承诺、人物信息时效等候选。这些不是快门现有人脉 v1 的新增承诺：先由人脉 owner 定义允许公开的最小投影；快门不推断私人关系，不自动发消息。[Monica Journals](https://docs.monicahq.com/vaults/journals)。

| 新场景 | 用户结果 | 契约前置 | 新验收对象 |
|---|---|---|---|
| 难卡/错题修复 | 回到出处、补理解、修订而保留历史 | cards/exam 困难项投影与编辑入口 | 修订前后版本、正式/预览调度区别 |
| 5/15/30 分钟学习 | 只进入可承担的集合 | owner 的到期/预计负担与集合选择 | 到时可停止、未做不算失败 |
| 会前准备 | 回忆上次互动和未完承诺 | contacts 最小公开摘要 | 看资料不写互动，私密备注不进通知 |
| 承诺回访 | 回到原互动并记录实际结果 | contacts/task owner 的日期和状态 | 改期/取消/多人参与不重复建提醒 |
| 项目切换/收尾 | 恢复资料与布局、决定暂停哪些提醒 | 雷切布局/上下文与各 owner 状态 | 不丢编辑、不删原文、可重新开启 |
| 打卡更正/周期变化 | 解释补记、更正、暂停对聚合的影响 | checkin owner 的更正/周期公开投影 | 中枢不重算 streak、不因改周期误补记 |

## 7. R85：AI 用户任务、证据与确认

MCP 官方说明 annotations 是行为提示，不能代替执行端权限控制，也不能让模型天然抵抗来源内容中的指令。拟研究的 AI 体验包括选择笔记/时间范围、预览会传出的上下文、来源与引用、只生成草稿、写入前对比和上下文变更后重新确认；已有服务器写防线继续沿用 R69/R78，新增对象是用户任务和多轮确认的可理解性。[MCP Tool Annotations](https://blog.modelcontextprotocol.io/posts/2026-03-16-tool-annotations/)。

本轮复核到 MCP 2026-07-28 的正式更新：无状态核心、显式应用 handle、多轮补充输入 MRTR、Tasks 扩展等，已经与本项目固定 2024-11-05 的实现存在代际差异。新增调研应把缺参数、等待用户、后台任务、取消和不同 host 的能力分开评估，保留老客户端路径；不能只替换协议版本字符串，也不能推断现有 host 全部已迁移。[MCP 2026-07-28 官方说明](https://blog.modelcontextprotocol.io/posts/2026-07-28/)。

快门仍是透传层：模型配置归思源/已有 AI host，思源内能力归雷切 Agent；新候选没有自建模型、再次保存 API Key 或自动扩大读范围的前提。来自网页、笔记正文和第三方工具描述的文本属于数据，不能授权新的写操作。

## 8. R86：无 Quicker、分享语义与低负担使用

Apple Shortcuts 根据声明的输入类型决定分享入口可见性，空输入可停止、询问或读取剪贴板；Drafts 则区分可编辑分享捕获和直接收进箱。对本项目应先定义文本/URL/图片/PDF/vCard 的接收合同，空输入不能静默用旧剪贴板；快速收进箱与精确归档分别研究点按数、错误率与回执发现性。[Apple 输入类型](https://support.apple.com/en-gb/guide/shortcuts/apd7644168e1/ios)、[限制输入与空输入](https://support.apple.com/en-ie/guide/shortcuts/apd8195f96d6/ios)、[Drafts Share/Quick Capture](https://docs.getdrafts.com/docs/extensions/share)。

Obsidian URI 提供跨应用导航/调用及部分 callback 行为，Workspaces 按任务保存布局。借鉴重点是回到来源应用、定位结果和恢复任务上下文，不等于给快门直接新增自定义写入 URL。无 Quicker 的 CLI、MCP、SiYuan 内入口需要逐任务验证最终结果，不能把 HTTP 200 当“该平台完整支持”。[Obsidian URI](https://help.obsidian.md/Extending+Obsidian/Obsidian+URI)、[Workspaces](https://obsidian.md/help/Plugins/Workspaces)。

## 9. R87/R88：长期收益、支持和维护成本

首跑成功之外，本项目需验证 7/30 天是否仍有真实任务使用、摘录后来是否被利用、全通知与仅错误通知的差别，以及净节省时间是否抵得上配置、学习、维护和失败恢复。上述指标是本轮研究推导，尚无实际样本或结果；可选本地计数和自愿访谈不能变成默认上传遥测。

教程应绑定具体插件包、动作 revision、公共协议和截图版本；旧教程保留适用版本与新版入口。反馈还需要明确问题归属和支持范围，减少用户在快门、Quicker、思源和上游插件之间反复求助；GitHub SUPPORT 文件提供集中入口的官方机制。[GitHub Support Resources](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/adding-support-resources-to-your-project)。

Drafts 的别名引用现有动作，分享目录保留来源以便更新，为动作单、教程和场景包共用权威定义提供参照。每个适配器/客户端都要记录校准工时、使用证据和退场条件；功能低采用或高维护时先说明替代与迁移，不突然删去用户配置。[Drafts Editing Actions](https://docs.getdrafts.com/docs/actions/editing-actions)、[Drafts Directory](https://docs.getdrafts.com/docs/extending/directory)。

## 10. 研究证据与下一步门槛

每个候选区分三层：①来源文档明确说明的行为；②结合本项目提出的设计假设；③尚缺公共契约/用户样本的条件。正式排期前需要一份输入/输出样例、正常与中断路线、owner/权限、可观察验收和维护估算。外部工具的付费、平台和协议限制须在实际选择时另行核对，本文不把它们列成必须购买或安装的依赖。

既有 R71~R79 保留原编号，本轮只新增独立对象；来源事实不能当成用户需求已成立的证据。后续可按“知识维护”“自动化治理”“离线连续性”“模块深层场景”选择最有真实频率的一条做产品验证，当前不执行开发。
